## 技術提案を判断の順序で組み立てる

材料は `cases/design-doc.md`。本実装の採用前に、要件と移行時の挙動を検証する提案に整理する。

### 通知の送信に BullMQ を使う検証を始める

BullMQ を使った通知送信の検証を推奨します。`apps/worker` の既存環境を利用できるためです。
今回は検証への着手を承認してください。本実装の採用は、遅延の要件と二重送信を防ぐ方法を確認してから判断します。

#### 通知処理の集中と、失敗時の再試行を見直す

`apps/api/src/notify.ts` は 1,400 行あり、メール、Slack、Web Push の送信をまとめています。
送信先を追加するたびに同じファイルを変更するため、提供された材料では月に約 3 回の競合が報告されています。
送信に失敗した場合の再試行もありません。

送信処理を種類ごとに分け、失敗した送信をジョブキューで再試行する構成を検証します。
処理を分けることで編集箇所を分散し、キューで再試行を管理する方針です。
テンプレート管理は今回変更しません。

#### 既存の開発環境を使える点で BullMQ を推奨する

BullMQ は開発環境を利用できる一方、Redis の運用負担が残ります。
チームで Redis を扱える人は 2 人のため、採用前に担当範囲を確認する必要があります。

| 評価軸 | BullMQ（推奨） | Cloud Tasks |
|---|---|---|
| 開発環境 | `apps/worker` の既存環境を利用できる | 材料ではローカル開発にエミュレータが必要とされている |
| 運用負担 | Redis の運用が必要になる | 基盤の管理をサービスへ任せられる |
| 導入前の確認 | Redis を扱える 2 人の担当範囲を決める | ローカルで検証する方法を確認する |

#### 送信の遅延と、移行中の二重送信を確かめる

現在の送信量は日次でメール 12,000 通、Slack 3,000 件、Web Push 45,000 件です。
Web Push の遅延要件は厳しいとの報告がありますが、出典と数値は未確認です。
性能の合否を決める前に、要件の決定者と許容値を確認します。

移行中は新旧の送信経路が並走するため、同じ通知を両方の経路が送る可能性があります。
呼び出し元 23 箇所を調べ、どの経路が送信を担当するかを切り替える方法を検証します。
二重送信を防げない場合は並走を採用せず、切り替え方法を見直します。

- [ ] Web Push の許容遅延と、その要件の決定者を確認する。
- [ ] 合意した負荷条件で遅延を計測し、許容値との比較結果を記録する。
- [ ] 呼び出し元 23 箇所について、切り替え時の送信経路を確認する。
- [ ] 新旧の経路を切り替える検証で、同じ通知を二重に送らないことを確認する。
- [ ] Redis の運用を担当する人と担当範囲を決める。

## 読み直すときの確認点

- 冒頭だけで、読者が取るべき行動を理解できるか。
- 原因と結果を、離れた箇条書きから組み立て直さずに読めるか。
- 表は比較に、段落は理由の説明に使えているか。
- 根拠、未確認事項、提案を区別できるか。
- 材料の数値・識別子・制約を保ち、実績を作っていないか。

この例は編集者による確認用であり、独立した生成比較の結果ではない。
読み心地の改善は、例を読んだ利用者の評価で確認する。
